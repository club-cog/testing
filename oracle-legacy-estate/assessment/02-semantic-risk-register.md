# Oracle to PostgreSQL semantic risk register

This register records differences that are exercised by this estate. It does not list generic migration concerns that have no source evidence.

| Risk | File and line | Oracle behavior in this estate | PostgreSQL behavior | What breaks silently under a naive translation | Required handling |
|---|---|---|---|---|---|
| Empty string is `NULL` | `ddl/001_tables.sql:10-11`, `ddl/001_tables.sql:40-41` | `DEFAULT ''` stores `NULL`. The checks `column <> ''` evaluate to unknown for `NULL`, so the defaulted rows pass. | PostgreSQL stores `''` as a value. The same checks evaluate false, so inserts using the default fail. | Address and customer inserts that work in Oracle can fail in PostgreSQL. If the checks are dropped, the target can instead retain empty values that never existed as distinct values in Oracle. | Decide whether these columns are nullable or require a nonempty value. Replace the defaults and checks with explicit `NULL`, `NULLIF(value, '')`, and a clear `NOT NULL` or nonblank rule. |
| Empty input changes order status | `packages/pkg_order_mgmt.pkb:18-34` | Oracle treats `p_requested_by = ''` as `NULL`; the procedure stores `BATCH` and chooses `OPEN`. | PostgreSQL treats `''` as non-null; a direct `COALESCE` and `CASE` rewrite would store an empty requester and choose `HELD`. | The same application payload creates a different order status without an error. | Normalize input with `NULLIF(btrim(p_requested_by), '')` if Oracle behavior is required, then derive status from the normalized value. |
| Empty payment method changes stored data and audit text | `packages/pkg_billing.pkb:117-147` | An empty `p_method` is null, so `NVL` stores and logs `UNKNOWN`. | `COALESCE('', 'UNKNOWN')` returns `''`. | Payments and audit payloads contain blank methods rather than `UNKNOWN`. | Normalize empty method input before `COALESCE`, or document an intentional contract change. |
| `DATE` carries time to the second | `ddl/001_tables.sql:13-14`, `42`, `60-61`, `73-74`, `91`, `141-142`, `175`, `192`, `206` | Oracle `DATE` stores calendar date and time to whole seconds, without a time zone. `SYSDATE` supplies the database server's local time. | PostgreSQL `date` stores no time. `timestamp without time zone` stores time but `CURRENT_TIMESTAMP` is transaction-start time and includes fractional seconds and a session time-zone conversion if cast. | Mapping by type name to PostgreSQL `date` truncates order, payment, audit, and validity times. Mapping every default to `CURRENT_TIMESTAMP` can also change repeated-call timing within a transaction. | Map timestamp-bearing columns to `timestamp(0) without time zone` unless a human chooses a time-zone model. Choose `clock_timestamp()` or `statement_timestamp()` where Oracle `SYSDATE` timing matters, and document the assumed source server zone. |
| Oracle date arithmetic uses days | `packages/pkg_billing.pkb:73-74`, `packages/pkg_customer_hier.pkb:50`, `app/raw_queries.sql:31` | Adding `30` or `1` to a `DATE` adds that many 24-hour days. Subtracting `90` applies an exact 90-day timestamp cutoff. | PostgreSQL does not add a bare integer to a timestamp. Date and interval expressions have different result types and daylight-saving implications for zoned timestamps. | Mechanical operator replacement can fail, truncate time, or move boundaries. The `BETWEEN :start_date AND :end_date + 1` query also includes exactly the next day's boundary. | Use explicit intervals such as `+ interval '30 days'` and `- interval '90 days'`. Confirm whether the raw query intends a closed range or the usual half-open range `>= start AND < end + interval '1 day'`. |
| Unbounded `NUMBER` has no declared integer size | `ddl/001_tables.sql:5`, `15`, `31`, `50`, `57`, `68-71`, `85`, `117-120`, `138`, `159-161`, `173`, `191`, `194`, `203-204` | `NUMBER` without precision can hold large integers or decimal values up to Oracle's numeric limits. The code mostly treats these columns as identifiers, counts, or quantities, but the DDL does not enforce that intent. | `bigint` is fixed-width and integral. PostgreSQL `numeric` is arbitrary precision but has different storage and performance. Identity columns require an integer type. | Choosing `bigint` can reject existing fractional or oversized values; choosing unconstrained `numeric` can preserve bad identifier data and complicate drivers and foreign keys. | Profile nonproduction data before final mapping. Tentatively use `bigint` for proven identifiers, integer or numeric for quantities based on observed scale, and add precision and scale only after evidence. |
| Mixed byte and character length semantics | `ddl/001_tables.sql:6-11`, `34-41`, `51-55`, `70`, `75`, `86`, `90`, `92-93`, `124`, `139`, `143`, `162`, `176-177`, `193`, `195-196` | `VARCHAR2(n BYTE)` limits encoded bytes while `VARCHAR2(n CHAR)` limits characters. | PostgreSQL `varchar(n)` limits characters, not encoded bytes. | Multibyte strings can be accepted in PostgreSQL even though Oracle would reject them, changing interface and index-size assumptions. | Preserve character limits with `varchar(n)`. Add byte-length checks using `octet_length` only where the Oracle byte ceiling is a real external contract. |
| `RAW(16)` has a fixed byte limit | `ddl/001_tables.sql:18`, `99`, `179`, `198` | `RAW(16)` accepts at most 16 bytes and is not inherently a UUID. | `bytea` has no built-in length limit; `uuid` imposes UUID interpretation and formatting. | A naive `bytea` mapping permits longer values. A naive `uuid` mapping can misinterpret opaque tokens. | Confirm the producer and meaning of each column. Use `bytea` plus `CHECK (octet_length(column) = 16)` for opaque fixed bytes, or `uuid` only with evidence. |
| `CLOB` and `BLOB` storage choices differ | `ddl/001_tables.sql:16-17`, `58-59`, `98`, `146-147`, `180`, `197` | Oracle LOBs use locator APIs and Oracle-managed storage. | PostgreSQL commonly uses TOAST-backed `text` and `bytea`; the separate large-object facility has different lifecycle and transaction rules. | Driver code and memory behavior can change even if values look identical. Large PDFs or images may not fit the chosen access pattern. | Measure nonproduction sizes and access patterns. Prefer `text` and `bytea` unless streaming requirements justify PostgreSQL large objects or external object storage. |
| `ROWNUM` is assigned before a query block's final ordering | `views/001_reporting_views.sql:34-46`, `packages/pkg_order_mgmt.pkb:123-143`, `app/raw_queries.sql:15-18` | The view nests the `ORDER BY` before applying `ROWNUM`. The package uses two levels to cap rows before selecting the requested range. The raw query applies an unordered cap. | PostgreSQL uses `LIMIT` and `OFFSET` after ordering. Window functions assign row numbers according to an explicit window order. | Flattening the nested Oracle queries can return a different set or page. The raw query remains nondeterministic unless ordered. | Rewrite the recent view as ordered `LIMIT 50`. Rewrite paging with `row_number()` or validated `LIMIT/OFFSET` and a stable tie-breaker such as `order_id`. Preserve the raw query's nondeterminism only if callers accept it. |
| `CONNECT BY` traversal direction and ordering | `packages/pkg_customer_hier.pkb:7-16`, `30-35`, `58-66`, `app/raw_queries.sql:20-27` | `START WITH` selects roots, `PRIOR` placement controls downward or upward traversal, `LEVEL` starts at 1, and `ORDER SIBLINGS BY` orders children. A cycle raises an Oracle error because `NOCYCLE` is absent. | Recursive CTEs require explicit anchor, join direction, depth, cycle detection, and output order. Row production order is not implied by recursion. | Reversing the join direction changes ancestors into descendants. Omitting a path sort changes display order. Omitting cycle handling can loop until a recursion or resource limit. | Write separate recursive CTEs for downward and upward traversal, carry depth and a path array, detect cycles, and order the printed tree by a sibling-order path. Decide whether to preserve Oracle's cycle error or return marked cycle rows. |
| `MINUS` set semantics | `packages/pkg_customer_hier.pkb:42-50` | `MINUS` returns distinct active-customer rows absent from the recent-order query and treats nulls as equal for set comparison. | PostgreSQL `EXCEPT` has the same distinct set shape, while anti-join rewrites can differ for duplicates and nulls. | Replacing the expression with an unchecked `NOT IN` can return no rows if the subquery ever contains null, and a `NOT EXISTS` rewrite can preserve duplicates if the left side changes later. | Use `EXCEPT` for the closest translation, or prove an anti-join equivalent against keys and nullability. Convert the 90-day cutoff separately. |
| `DUAL` and expression selects | `packages/pkg_order_mgmt.pkb:18-20`, `packages/pkg_billing.pkb:51-53`, `app/raw_queries.sql:34-35` | Oracle requires `FROM DUAL` for these scalar selects. | PostgreSQL permits `SELECT expression` without a table. | Keeping `DUAL` fails unless an unnecessary compatibility object is created. A compatibility table can also introduce permissions and naming baggage. | Remove `FROM DUAL`. Where the select only computes a local value, prefer direct PL/pgSQL assignment. |
| Legacy `(+)` outer joins | `ddl/003_derived_objects.sql:15-17`, `views/001_reporting_views.sql:16-18`, `28-32`, `packages/pkg_order_mgmt.pkb:198-204`, `app/dao.py:71-75`, `app/raw_queries.sql:3-13` | `(+)` marks the nullable side of an Oracle outer join. Predicate placement is part of the semantics. | PostgreSQL requires ANSI `LEFT JOIN` or `RIGHT JOIN` syntax. Filters in `WHERE` versus `ON` can turn an outer join into an inner join. | Rows without invoices or orders can disappear if predicates move to the wrong clause. Chained joins in `V_CUSTOMER_BALANCE` are especially easy to alter. | Rewrite each join explicitly and compare result sets. Keep predicates on optional tables in their `ON` clauses unless the Oracle query intentionally filters null-extended rows. |
| Balance view multiplies invoice totals by payment rows | `views/001_reporting_views.sql:20-32` | Oracle joins invoice rows to every payment row before summing. An invoice with three payments contributes its `invoice_total` three times. | PostgreSQL will do the same under a faithful join rewrite. | A migration team may "fix" the query accidentally, or may preserve a likely defect without recognizing it. Either choice changes reported balances relative to an intended model. | Treat this as a business decision, not a syntax conversion. Compare Oracle outputs to independently aggregated invoice and payment totals on nonproduction data, then obtain owner approval for preserve versus correct. |
| Optimizer hints are executable guidance only in Oracle | `packages/pkg_order_mgmt.pkb:126`, `app/raw_queries.sql:3` | Oracle can use `FIRST_ROWS` and the named order index as optimizer hints. | PostgreSQL treats the hint comment as an ordinary comment unless a non-core extension is installed. | Queries still run but may have different latency, plan stability, and page-first behavior. | Remove Oracle hints from target SQL. Create indexes from access patterns, gather statistics, and validate `EXPLAIN (ANALYZE, BUFFERS)` with representative data. Do not assume the Oracle hint's index is optimal in PostgreSQL. |
| Package-level state is session-scoped | `packages/pkg_order_mgmt.pks:2`, `packages/pkg_order_mgmt.pkb:3`, `16`, `40`, `packages/pkg_billing.pkb:3`, `82`, `185-187` | `g_last_order_id`, `g_call_count`, and `g_run_label` live in package state for an Oracle database session. State persists across calls and can leak across logical requests when a pool reuses a session. | PostgreSQL has schemas and functions, but no equivalent package variable lifecycle. Temporary settings or tables have different visibility and pooling behavior. | Removing state changes `DBMS_OUTPUT` text. Replacing it with process globals can leak across database sessions or workers. Replacing it with a table introduces concurrency and cleanup issues. | Determine whether any external caller reads `g_last_order_id` and whether output labels matter. Prefer explicit parameters and return values. If compatibility state is required, design a session-scoped mechanism and test it with the actual pooler mode. |
| Autonomous audit transaction | `packages/pkg_billing.pkb:5-35` | The log insert commits independently of the caller. It remains after the invoice or payment transaction rolls back. All logging errors are suppressed. | PL/pgSQL functions and procedures do not provide Oracle's same-session autonomous transaction. A normal insert participates in the caller transaction. | Audit rows disappear on business rollback, or an attempted internal commit fails. Making logging synchronous can also cause business operations to fail, unlike the source. | Choose deliberately: separate database connection, `dblink`, an outbox processed after commit, or transactional logging. Preserve error suppression only if owners confirm that silent audit loss is acceptable. |
| Savepoint rollback inside exception handlers | `packages/pkg_order_mgmt.pkb:15`, `45-51`, `154`, `170-173` | The procedures establish a savepoint and roll back only their work while leaving the caller's earlier transaction intact. They then raise an Oracle application error or rethrow. | PL/pgSQL exception blocks use subtransactions. Transaction control and explicit savepoint commands are restricted inside functions, and procedure behavior depends on how it is called. | A naive function can roll back too much, fail to compile, or leave partial work. The DAO's commit placement means transaction boundaries span multiple package calls. | Define the target API as functions or procedures together with caller transaction ownership. Use exception-block subtransactions for local rollback where possible, and integration-test the complete `process_order` transaction sequence. |
| Reverse numeric `FOR` loop bounds differ | `packages/pkg_order_mgmt.pkb:194-196` | Oracle `FOR i IN REVERSE 1..N` visits `N` down to `1`. Because of `GREATEST(l_line_count, 1)`, it runs once even when the order has no lines. | In PL/pgSQL, a reverse loop conventionally starts with the first expression and decrements toward the second, so a textual `REVERSE 1..N` does not express the Oracle range for `N > 1`. | The marker can remain `LINE-1` or the loop can execute the wrong number of times instead of ending at the highest line count. | Rewrite the bounds explicitly for PostgreSQL, for example from `GREATEST(count, 1)` down to `1`, and add tests for zero, one, and several lines. |
| Dynamic SQL concatenates an identifier | `packages/pkg_order_mgmt.pkb:12-13`, `38-40` | The table name `ORDERS` is concatenated into a statement. It is currently a package-local constant, not caller input. Bind variables protect the order-number value only. | PostgreSQL dynamic SQL requires `EXECUTE`; identifiers must be quoted separately from values. | A future variable table name can create injection or case-folding bugs. Quoting the whole string as a value produces invalid SQL. | Remove the dynamic SQL because the table is constant. If later requirements make the identifier variable, use `format('%I', identifier)` and `USING` for data values. |
| Dynamic SQL is unnecessary but used with bulk fetch | `packages/pkg_billing.pkb:163-168` | Oracle parses a text statement, bulk-collects two collections, and binds the invoice identifier. | PL/pgSQL can loop dynamic query rows, but has no direct `BULK COLLECT` construct and does not need dynamic SQL for a fixed table. | A line-by-line emulation adds overhead and can change empty-result behavior. | Replace the whole routine with set-based updates and aggregates. If arrays are retained, define and test their ordering and empty-array behavior. |
| `BULK COLLECT` and `FORALL` collection semantics | `packages/pkg_order_mgmt.pkb:149-169`, `packages/pkg_billing.pkb:158-178` | Oracle materializes dense collections and executes bulk DML over index bounds. Collection count and exception behavior determine whether an empty source is harmless or raises at the `FORALL` range. | PostgreSQL favors set-based DML. Arrays and `FOREACH` have different indexing and error behavior. | Per-row loops can be much slower. Empty-customer or empty-invoice cases can change from error to success, or the reverse, without notice. | Use `INSERT ... SELECT`, aggregate `UPDATE`, or `UPDATE ... FROM` statements. Run the Oracle routines with empty and nonempty source sets to establish the source contract before final equivalence claims. |
| `DBMS_LOB` temporary CLOB lifecycle | `packages/pkg_billing.pkb:43-44`, `55-56`, `85-92` | The procedure allocates a temporary CLOB locator, appends text, stores it, and explicitly frees the locator in success and error paths. | PostgreSQL `text` values do not require locator allocation or freeing. PostgreSQL large objects use unrelated APIs and ownership. | A literal API translation adds locator lifecycle code that does not match either common PostgreSQL storage choice. | If `delivery_note` maps to `text`, construct the value directly. If external size evidence requires large objects, redesign around PostgreSQL's large-object API and driver behavior. |
| `DBMS_OUTPUT` is not a normal result channel | `packages/pkg_order_mgmt.pkb:42-44`, `169`, `189-211`, `packages/pkg_billing.pkb:185-187`, `packages/pkg_customer_hier.pkb:18-21` | Text is buffered per Oracle session and appears only when a client enables and reads `DBMS_OUTPUT`. | `RAISE NOTICE` goes through server messages and has different filtering and driver access. Result sets or logs are explicit interfaces. | Replacing calls with notices can lose output, pollute logs, or expose different data. Dropping them can remove an operational dependency not visible in the included app. | Classify each call as debug text, operator logging, or caller output. Remove debug-only calls, use structured logging for operations, and return rows for functional output. Confirm external consumers first. |
| Sequence and trigger key assignment overlap | `triggers/001_key_assignment.sql:3-60`, `triggers/002_derived_values.sql:31-42`, `packages/pkg_billing.pkb:51-80`, `117-132`, `app/raw_queries.sql:34-35` | Triggers allocate only when a key is null. Billing sometimes supplies explicit `NEXTVAL` values. `ISSUE_INVOICE` depends on `CURRVAL` from its earlier `NEXTVAL`. Application SQL consumes `SEQ_ORDERS` without inserting a row. | PostgreSQL identity columns can be `ALWAYS` or `BY DEFAULT`; explicit sequence calls and trigger assignment are separate choices. `currval` remains session-specific but fails before `nextval`. | An `IDENTITY ALWAYS` target rejects existing explicit IDs. Independent identity and named sequences can diverge. Consuming a sequence for a proposed order number creates gaps, which may surprise callers. | Use one owned sequence per key and choose `BY DEFAULT` identity or a compatible before-insert trigger where explicit IDs must remain valid. Set each sequence above loaded data. Keep business display numbers separate from surrogate-key allocation if gaps are unacceptable. |
| Some declared sequences have no included assignment path | `ddl/002_sequences_indexes.sql:7`, `10`; `ddl/001_tables.sql:67-82`, `158-170` | `SEQ_PRICE_TIERS` and `SEQ_INVOICE_LINES` exist, but no included trigger, package, or application statement uses them. | PostgreSQL will not infer that these sequences belong to columns unless ownership or defaults are declared. | Migrated inserts can receive null-key errors, or teams may wire a sequence that external loaders intentionally control. | Search scheduler, loader, and integration repositories. Until callers are known, record the sequences but do not claim the target key-generation contract is complete. |
| IOT storage has no direct target object | `ddl/001_tables.sql:114-135` | `ORDER_LINES` stores table rows in the primary-key B-tree and can place trailing columns in overflow storage. Oracle heap `ROWID` assumptions do not apply normally to an IOT. | PostgreSQL stores table rows in a heap. A primary-key B-tree is separate. `CLUSTER` is a one-time physical rewrite and is not maintained. | A tool can silently emit a heap table and claim equivalence while changing locality, write amplification, and any hidden row-identifier assumptions. | Create a normal table with the same primary key first. Test access paths and size on representative data. Search all external code for `ROWID` before deciding whether additional clustering or covering indexes are useful. |
| Oracle bitmap index has no PostgreSQL counterpart | `ddl/002_sequences_indexes.sql:25` | A stored bitmap index targets low-cardinality `order_status`. It can be efficient for analytic combinations but costly under concurrent DML. | PostgreSQL can create bitmap scan plans by combining ordinary indexes, but it has no stored bitmap index type. | Replacing it with a same-named B-tree may add write cost without helping, while dropping it may slow reporting. | Use workload and cardinality evidence to choose among the existing `(order_status, ordered_at)` B-tree, partial indexes for selected statuses, or no extra index. |
| Materialized view refresh model and locking | `ddl/003_derived_objects.sql:5-23`, `docs/estate-notes.md:8-15` | The view is built immediately and fully refreshed only on demand. The included source does not show who refreshes it. | PostgreSQL `REFRESH MATERIALIZED VIEW` also recomputes data, but blocks readers unless `CONCURRENTLY` is used. Concurrent refresh requires a qualifying unique index on the materialized view. | The target view can remain stale forever, or refreshes can block billing screens. The existing nonunique index on `order_total` cannot enable concurrent refresh. | Find the scheduler and freshness contract. Add a unique index on `customer_id` only if data proves it is unique, decide refresh cadence and ownership, and test refresh duration and read availability. |
| Trigger reads its own mutating table | `triggers/002_derived_values.sql:1-16` | An Oracle row trigger queries `ORDER_LINES`, the table currently being changed. This is expected to raise `ORA-04091` for affected inserts or updates unless omitted source objects change the behavior. | PostgreSQL row triggers may query the target table, but visibility and multi-row statement behavior still require care. | A direct PostgreSQL port can make formerly failing Oracle writes succeed, while preserving the trigger can calculate partial totals once per row during multi-row statements. | Confirm the Oracle failure with an instance. Replace row-by-row aggregation with a statement-level transition-table trigger, an explicit service routine, or deferred recalculation. Do not label a successful PostgreSQL port equivalent until the source defect decision is approved. |
| Trigger and package disagree on order totals | `triggers/002_derived_values.sql:5-16`, `packages/pkg_order_mgmt.pkb:89-109` | The trigger sets subtotal and total to the raw sum of `extended_amount`. The package later subtracts discounts and adds 8.25 percent tax. Direct updates only invoke the trigger. | PostgreSQL will preserve whichever logic is translated, but not both as one coherent rule. | Totals depend on the write path. A mechanical translation can lock in inconsistent values or change which calculation wins. | Choose one authoritative calculation. Prefer a set-based routine or generated input model, then route every writer through it and reconcile existing rows. |
| Payment trigger and package disagree on `VOID` | `triggers/002_derived_values.sql:20-27`, `packages/pkg_billing.pkb:117-141` | The trigger preserves `VOID`, but after it runs the package unconditionally changes the invoice to `PAID` or `PARTIAL`. The inserted payment is only `PENDING` when the prior invoice status is `VOID`. | A faithful PostgreSQL rewrite preserves the contradiction. A trigger-only or package-only rewrite changes it. | A payment attempt can unvoid an invoice even though the inserted payment is not captured. | Ask the billing owner whether payments against void invoices must be rejected, retained as pending, or allowed to reopen invoices. Implement one rule and test it explicitly. |
| `SYS_CONTEXT` user identity | `packages/pkg_billing.pkb:27` | The audit actor is the Oracle session user, falling back to `BATCH` only if it is null. With a shared service account this may not identify the human or job. | PostgreSQL `session_user` and `current_user` have different role-switch behavior. Application user identity is not automatically available. | Audit actor values can change at cutover or remain a generic service principal while owners assume they identify a person. | Decide whether the actor is database principal, application principal, or job name. Pass application identity explicitly if required, and map Oracle session-user semantics only when that is the intended source behavior. |
| Ref cursor and procedure call contract | `packages/pkg_order_mgmt.pks:22-27`, `packages/pkg_customer_hier.pks:6-13`, `app/dao.py:58-65` | Oracle procedures return `SYS_REFCURSOR` through an `OUT` parameter, and the Python driver fetches the cursor variable. | PostgreSQL can return a set directly, return a named cursor that is transaction-scoped, or use a procedure with output parameters. Driver calls differ. | Keeping a cursor name without an open transaction fails at fetch time. Changing to a set-returning function breaks `callproc` signatures. | Choose the target API with the application conversion. | Error-code and exception semantics | `packages/pkg_order_mgmt.pkb:45-51`, `170-173`, `packages/pkg_billing.pkb:88-94`, `148-152` | Oracle raises named exceptions and application errors in the `-20901` to `-20912` range, while some handlers preserve the original error and logging suppresses all errors. | PostgreSQL uses SQLSTATE, exception conditions, and message fields. Numeric Oracle codes have no automatic equivalent. | Applications can receive different exception classes or lose the distinction between duplicate order, missing invoice, and internal failure. | Define a target SQLSTATE and message contract, preserve stable business error identifiers, and update application exception handling. Keep original diagnostic context in server logs without exposing sensitive values. |

## Risks that need source execution

Several entries can be reasoned about from code but not fully proved without Oracle. The mutating-table trigger, empty-collection `FORALL` behavior, savepoint boundaries, package state across pooled sessions, and optimizer plans need execution on an Oracle instance with nonproduction or synthetic data. Those tests are part of the migration plan rather than this read-only phase.
