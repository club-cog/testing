# Oracle to PostgreSQL migration wave plan

## Planning basis

The supplied estate contains 52 source-defined schema objects and 14 public package routines. It also includes a small Python application tier with direct Oracle SQL and package calls.

This plan separates three workstreams that must converge before cutover:

1. Schema and data migration.
2. Stored procedure, trigger, view, and query conversion.
3. Application driver, transaction, and call-site conversion.

Phase 0 did not convert code. The sequence below starts with decisions and executable baselines because several source rules conflict or appear unable to run as written.

## Wave 0: establish the source baseline

### Why this comes first

Code review found likely source defects and missing runtime dependencies. Without a source baseline, a PostgreSQL implementation can be internally reasonable but cannot be called equivalent.

### Work

- Obtain an Oracle 19c-compatible nonproduction instance and load the exact estate.
- Record exact Oracle version, patch level, character set, national character set, database time zone, session time zone, and relevant NLS settings.
- Compile every object and capture status and compiler errors.
- Exercise the mutating `TRG_ORDER_LINES_AI` path with single-row and multi-row inserts and updates.
- Exercise every public routine with normal, null, empty-string, missing-row, duplicate, zero-row, and multi-row cases.
- Capture package state behavior across repeated calls and connection-pool reuse.
- Capture transaction outcomes for the full worker flow, including failure after each commit point.
- Export object grants, synonyms, scheduler jobs, materialized-view refresh metadata, database links, and dependent objects in other schemas.
- Capture row counts, null counts, numeric ranges and scales, string byte and character lengths, LOB size distributions, hierarchy cycles, orphan checks, duplicate business keys, and sequence current values.
- Capture representative Oracle plans and timings for paged orders, recent orders, hierarchy traversal, balance reporting, and materialized-view refresh.

### Exit evidence

- A repeatable Oracle setup or a controlled schema export.
- Source test cases with expected results and errors.
- An approved list of source defects to preserve temporarily or correct during migration.
- A dependency list that includes schedulers, reports, loaders, and other schemas.

## Wave 1: decide the target contract

### Why this precedes DDL conversion

Type choices, identity behavior, package API shape, transaction ownership, and defect policy affect nearly every later object.

### Human decisions

- Map each unbounded `NUMBER` column to `bigint`, integer, or constrained `numeric` using data evidence.
- Choose `timestamp(0) without time zone` versus a time-zone-aware model, and define the source server zone.
- Decide which Oracle byte limits remain external contracts.
- Decide whether each `RAW(16)` value is opaque bytes or a UUID.
- Choose `text` and `bytea`, PostgreSQL large objects, or external storage for LOB columns.
- Decide whether callers may continue supplying explicit keys.
- Decide whether order and invoice display numbers share surrogate-key sequences or receive separate business-number generators.
- Choose target interfaces for procedures and ref cursors, preferably set-returning functions for read APIs and explicit transaction-owned service operations for writes.
- Replace package state with explicit inputs and outputs, or approve a session-scoped compatibility design.
- Choose an audit model: autonomous separate connection, transactional audit, or outbox.
- Approve preserve-versus-correct decisions for every rule flagged in `05-business-rules.md`.
- Decide whether `CURRENT_ORDERS` becomes a compatibility view, a renamed table reference, or an application change.
- Define materialized-view freshness, refresh owner, and reader availability during refresh.

### Exit evidence

- Signed type-mapping matrix.
- Signed API and transaction contract.
- Signed business-rule disposition list.
- Target naming and compatibility policy.

## Wave 2: build the base schema and data path

### Why this converts first

Packages, views, triggers, and application calls all depend on stable table, key, type, and data-load contracts.

### Work

- Create the 10 persistent tables and one PostgreSQL design for `GTT_ORDER_TOTALS`.
- Implement primary, unique, foreign-key, check, and non-null constraints after resolving empty-string behavior.
- Create owned sequences or `GENERATED BY DEFAULT AS IDENTITY` columns according to the explicit-ID decision.
- Map `ORDER_LINES` to a heap table with its composite primary key. Do not emulate IOT storage before workload tests.
- Create the ordinary B-tree and unique indexes, but defer the Oracle bitmap-index replacement.
- Add fixed-byte checks for opaque 16-byte values if `bytea` is selected.
- Write repeatable migration scripts under the repository's chosen migration tool and run them in CI.
- Build an extract, transform, and load process that normalizes Oracle empty strings to null and preserves timestamp seconds.
- Load parent tables before children, then set every sequence above the loaded maximum.
- Reconcile source and target row counts, keys, foreign keys, null counts, sums, minimums, maximums, and hashes appropriate to each table.

### Special handling

- Do not add a `PRICE_TIERS.TIER_ID` or `INVOICE_LINES.INVOICE_LINE_ID` default until omitted loader behavior is understood.
- Do not create a PostgreSQL temporary table on every pooled request without defining who creates, reads, clears, and drops it.
- Defer address-to-order customer ownership constraints unless owners approve a new rule.

### Exit evidence

- Clean schema creation on an empty PostgreSQL database.
- Repeatable data load.
- Automated reconciliation report.
- Sequence synchronization proof.

## Wave 3: convert declarative reads

### Why before write routines

Views and read-only functions are easier to compare without trigger and transaction side effects. They also expose type and join mistakes early.

### Work

- Rewrite all `(+)` joins as explicit ANSI joins with optional-side predicates in `ON`.
- Convert `V_RECENT_ORDERS` to an ordered limit and add an approved tie-breaker.
- Convert paged-order SQL using `LIMIT/OFFSET` or `row_number()` with deterministic ordering.
- Convert hierarchy queries to recursive CTEs with explicit direction, depth, sibling-order path, and cycle handling.
- Convert `MINUS` to `EXCEPT`.
- Remove `DUAL`, `NVL`, `NVL2`, `DECODE`, and Oracle hints with case-specific PostgreSQL expressions.
- Decide and implement the correction or compatibility version of `V_CUSTOMER_BALANCE`.
- Create the materialized view only after refresh ownership is known. Add a qualifying unique index if concurrent refresh is required and the row key is proved unique.
- Replace `CURRENT_ORDERS` according to the compatibility decision.

### Validation

- Run each Oracle and PostgreSQL query against matched nonproduction data.
- Compare ordered result sets, duplicate counts, null placement, numeric scale, and boundary timestamps.
- Compare plans and timings after PostgreSQL statistics are representative.

### Exit evidence

- Result-set equivalence report for every view and read routine.
- Approved exceptions for intentional bug fixes.

## Wave 4: convert business writes and transaction behavior

### Why after reads and schema

The write routines depend on final keys, types, constraints, and approved business formulas.

### Work

- Replace `PKG_ORDER_MGMT.CREATE_ORDER` with a target routine or application transaction that returns the new key and exposes stable business errors.
- Remove its constant-table dynamic SQL.
- Replace line-number `MAX + 1` with a concurrency-safe design, such as locking the order row or maintaining a per-order counter, after owner approval.
- Establish one authoritative order-total calculation and remove or redesign conflicting trigger logic.
- Replace the mutating row trigger with statement-level set-based maintenance, explicit service calls, or another approved model.
- Convert temporary total loading to set-based SQL. Preserve session and commit semantics only if an actual caller needs them.
- Replace `DBMS_OUTPUT` functional reports with returned rows. Send operational messages to structured logging only when required.
- Convert invoice issuance without temporary CLOB APIs when `DELIVERY_NOTE` maps to `text`.
- Convert payment application with an approved `VOID`, pending, reversal, and overpayment policy.
- Convert invoice total rebuilding to aggregate `UPDATE` statements rather than collections and `FORALL`.
- Implement the chosen audit transaction model and test parent rollback behavior.
- Map Oracle application errors to documented SQLSTATE values or application error identifiers.

### Transaction tests

For each write API, test:

- Success.
- Duplicate business key.
- Missing parent.
- Null and empty-string input.
- Constraint failure after some work.
- Concurrent line creation.
- Concurrent payment.
- Caller rollback after success.
- Audit failure.
- Connection reuse through the actual pooler.

### Exit evidence

- Routine-level equivalence and concurrency tests.
- Approved transaction-boundary diagrams.
- No unresolved trigger and package rule conflicts.

## Wave 5: convert the application tier

### Why after target APIs stabilize

The Python call signatures, cursor handling, commits, and direct SQL all depend on the chosen PostgreSQL interfaces.

### Work

- Replace `oracledb` or `cx_Oracle` with the approved PostgreSQL driver and connection configuration.
- Replace `callproc` and Oracle cursor variables with target function, procedure, or SQL calls.
- Rewrite direct SQL in `app/dao.py` and `app/raw_queries.sql`.
- Remove `NVL`, `(+)`, `ROWNUM`, `CONNECT BY`, `DUAL`, sequence syntax, and Oracle bind assumptions.
- Redesign `process_order` transaction scope. Prefer one explicit business transaction unless owners confirm the current partial-commit behavior.
- Add application tests for order creation, multiple lines, no lines, invoice issuance, optional payment, paging, and rollback.
- Search deployment files and other repositories for the additional connection factory mentioned in `docs/estate-notes.md:17-18`.

### Exit evidence

- Application integration tests pass against PostgreSQL.
- No Oracle driver, DSN, package call, Oracle SQL syntax, or direct Oracle sequence reference remains in deployed paths.
- Transaction outcomes match the approved contract.

## Wave 6: performance, operations, and cutover rehearsal

### Work

- Load representative nonproduction volume.
- Validate B-tree and partial-index choices. Do not create a replacement for `BIX_ORDERS_STATUS` without plan evidence.
- Measure order paging, hierarchy traversal, balance reporting, payment locking, line updates, and materialized-view refresh.
- Define autovacuum, analyze, backup, restore, monitoring, and connection-pool settings.
- Rehearse a full load plus incremental catch-up if downtime cannot cover the load.
- Reconcile rows and business aggregates after rehearsal.
- Run the application and external reports against the target.
- Rehearse rollback to Oracle and document the point after which rollback needs reverse replication or manual repair.

### Exit evidence

- Performance thresholds met.
- Operational runbook approved.
- Cutover and rollback rehearsals completed.
- Business owner signs off on result comparisons and intentional behavior changes.

## What cannot be proved from the supplied source

An Oracle instance and nonproduction or synthetic data are required to prove:

- Whether every source object compiles and is valid.
- The exact runtime error from `TRG_ORDER_LINES_AI` and whether an omitted object changes it.
- Empty-collection behavior in the two `FORALL` routines.
- Package state behavior under the actual application connection pool.
- Exact savepoint and commit outcomes across the worker flow.
- Current row counts, invalid data, hierarchy cycles, duplicates, LOB sizes, and numeric scales.
- Actual character set effects on byte-limited columns.
- Oracle server time zone, session time zone, and NLS-dependent formatting or comparison.
- Current sequence values and whether external loaders reserve ranges.
- Optimizer plans, index usefulness, and data distribution.
- Materialized-view refresh duration, freshness, scheduler, and reader impact.
- Grants, roles, database links, scheduler jobs, external reports, and objects in other schemas.
- Calls to the seven public routines that have no caller in this repository.
- Whether `CURRENT_ORDERS`, package state, or `DBMS_OUTPUT` is consumed externally.
- Whether source defects are visible to users or hidden by deployment differences.
- Result equivalence for business reports and write workflows.

## Open questions

### Ownership and scope

1. Who owns order, billing, customer hierarchy, and reporting rule decisions?
2. Where is the scheduler that calls `PKG_BILLING`, and which routines does it invoke?
3. Which reports or other schemas reference `CURRENT_ORDERS`, the views, materialized view, packages, or sequences?
4. Are there loaders for customers, addresses, products, price tiers, and invoice lines outside this repository?
5. Are grants, database links, public synonyms, scheduler jobs, or ORM mappings in scope?

### Data and types

6. What are the maximum, minimum, fractional scale, and null distributions for every unbounded `NUMBER` column?
7. What time zone does each `DATE` value represent, and do users expect whole-second precision?
8. Are the `RAW(16)` columns UUIDs, hashes, gateway bytes, or opaque tokens?
9. What are the maximum and percentile sizes of each CLOB and BLOB?
10. Are Oracle byte limits contractual for external integrations?
11. Do existing hierarchy cycles, orphan references, duplicate logical keys, or negative monetary values exist?

### Keys and storage

12. Must callers continue to insert explicit primary keys?
13. How are `PRICE_TIERS.TIER_ID` and `INVOICE_LINES.INVOICE_LINE_ID` assigned today?
14. Is advancing `SEQ_ORDERS` to propose an order number intentional, and are gaps acceptable?
15. Does any external code depend on Oracle `ROWID` or IOT physical behavior?
16. What workload justified the bitmap index, and is the orders table write-heavy?

### Business behavior

17. Should `DESCENDANT_COUNT` include the root?
18. What do customer status values `A`, `I`, and `H` mean?
19. Are `ZZ`, `UNKNOWN`, and `BATCH` approved domain values or placeholders?
20. Should bill and ship addresses be required to belong to the order's customer?
21. How should overlapping price tiers be selected, and must product active state be checked during ordering?
22. Is order tax always 8.25 percent, and can the rate vary by address, product, or date?
23. Is `ORDER_LINES.EXTENDED_AMOUNT` before or after discount?
24. Which order-total implementation is authoritative: the package or the trigger?
25. Should `V_CUSTOMER_BALANCE` preserve its repeated invoice totals or be corrected?
26. Is invoice total tax-inclusive, and what exactly does `TAX_TOTAL` represent?
27. Who creates invoice lines, and must each line reference the order's matching line?
28. What should happen when a payment targets a void invoice?
29. Are overpayments allowed, and how are refunds or reversals reflected in invoice status?
30. Is losing an audit event silently acceptable?

### APIs and transactions

31. Which `DBMS_OUTPUT` text is read by a caller rather than used for debugging?
32. Does any caller read public package variable `PKG_ORDER_MGMT.G_LAST_ORDER_ID`?
33. Must Oracle numeric application error codes remain visible to callers?
34. Should order creation, all lines, invoice issuance, and optional payment be one atomic transaction?
35. Who reads `GTT_ORDER_TOTALS`, and must rows disappear on commit?
36. Which target pooling mode will be used, and can any compatibility design rely on session affinity?

### Materialized view and operations

37. Who refreshes `MV_CUSTOMER_ORDER_ROLLUP` today?
38. What freshness target and refresh window do billing screens require?
39. Can readers be blocked during refresh, or is concurrent refresh required?
40. What data volume, growth rate, downtime window, recovery point, and recovery time govern cutover design?
